# 逐层解析与反例：A04 和 A06 怎样避免看错字节

这节以边界检查为主线，把协议解析、过滤和异常测试联系起来。课程依据：PDF p9、p14–15；p14的流追踪与进程关联属于加分。

## 解析先回答“还能读多少”

偏移offset表示当前字段从第几个字节开始。长度length表示需要读取多少字节。程序必须先确认 offset 不超过已捕获长度，再确认 length 不超过剩余长度，然后才能读取。

捕获长度caplen表示文件中真正存在多少字节；原始长度表示捕获系统报告原报文有多长。若只捕获了一部分，不能用原始长度为索引提供保证。来自报文的IP总长、TCP头长也都不可信，需逐层与现有字节核对。

边界检查顺序：链路类型与最小头长；网络版本与头长；网络层声明长度；分片/扩展头；传输层最小头长与可变长度；应用层可见载荷。每层缩小下一层能够读取的范围。

## 字节序为什么会让数字变错

同一整数可以按高位字节先存或低位字节先存。网络中的许多多字节字段使用大端序，Windows常见CPU使用小端序。读取端口或长度时需要按照字段规定组合，不能把任意字节地址强转为整数指针。

例如两字节 `00 35` 按大端表示53。读反就变成另一数值。测试不仅比较“成功/失败”，还要逐项比较端口与长度，才能发现这种错误。

## IPv4与IPv6不是换一套地址显示格式

IPv4头长由IHL决定，选项会使它长于20字节。IPv6基础头为40字节，后面可能有扩展头链。解析IPv6需根据Next Header逐段推进，检查每段长度并限制遍历次数。

IP分片使一个原始IP数据报分散到多个片。非首片通常没有完整的TCP/UDP头，不能把分片载荷开头误读成端口。本项目基础范围只标记分片及不能确认的内容，不承诺IP重组。

TCP把应用数据组织为字节流。一次HTTP头可能分散在多个TCP段中。当前不做完整流重组时，仅对已连续可见的完整明文特征给出有限HTTP识别，并明确跨段与加密的未知边界。

## 端口不能证明应用协议

HTTP可以出现在非80端口；80端口也可以承载其他数据。单看端口会同时产生漏报和误报。基础识别需要检查可见请求行/响应行等内容，但也应承认启发式识别的覆盖范围。

捕获过滤和显示过滤处于不同位置。捕获过滤判断原始包能否进入应用；显示过滤根据解析结果选择当前界面行。HTTP不是普通BPF端口表达式的同义词。本项目的显示过滤语法也不能冒充完整Wireshark语法。

## 为什么要区分四种状态

| 状态 | 意义 | 展示原则 |
| --- | --- | --- |
| valid | 当前支持范围内的检查通过 | 仍不宣称完整协议栈验证 |
| truncated | 捕获字节不足 | 显示已可靠读取的字段，停止越界读取 |
| malformed | 已有字段互相矛盾或不合法 | 显式给出原因，不伪造缺失值 |
| unsupported | 类型或能力超出实现范围 | 保留原字节，说明无法继续 |

这些状态比单一“解析失败”更有用，因为它们帮助定位问题。字段值与状态必须一起查看：有源地址不代表TCP头也完整。

## 用什么反例推翻错误实现

为IPv4 IHL、IP总长、TCP data offset、UDP长度、IPv6扩展头各准备边界前后输入。加入截断、非首片、未知链路类型、损坏PCAP，以及“80端口非HTTP”“非80端口HTTP”。固定输入哈希，预先写出应得到的状态或帧编号集合。

与TShark存在差异时，先检查重组设置和协议识别策略，再回到原字节。不把两者不一致自动视为本程序错误，也不把本程序声明的限制当作所有差异的免检理由。

## 展示一个能解释机制的例子

报告选择一帧，列“偏移、长度、原字节、解释、独立值”。PPT展示该帧的三栏截图，标出链路头与IP起点，再用两个HTTP端口反例说明方法取舍。异常展示可选择真实截断输入，不需要伪造一次bug故事。

> [!example]- 自测：caplen=30，IP字段声称总长=100，能直接读第80字节吗？
> 不能。字段声称长度不能创造实际不存在的字节。应先检查链路头和IP头是否完整，再根据捕获剩余长度标记截断。原始长度和协议声明长度都不能替代caplen。

补充原始依据：[IPv4 RFC791](https://www.rfc-editor.org/rfc/rfc791)、[IPv6 RFC8200](https://www.rfc-editor.org/rfc/rfc8200)、[UDP RFC768](https://www.rfc-editor.org/rfc/rfc768)、[TCP RFC9293](https://www.rfc-editor.org/rfc/rfc9293.html)、[HTTP/1.1 RFC9112](https://www.rfc-editor.org/rfc/rfc9112)、[Wireshark显示过滤](https://www.wireshark.org/docs/wsug_html_chunked/ChWorkBuildDisplayFilterSection.html)。

## 本次实际排障：错误也可能在预期答案里

首次完整回归曾在 capture-udp.membership 失败。最初expected把“被解析器理解为UDP”和“裸BPF表达式udp会放行”当成同一集合。没有为了让测试变绿去改解析器；先检查独立工具编译出的BPF指令，再按固定PCAP原字节计算分支。

本机libpcap 1.10.5的这条BPF表达式会检查Ethernet类型与固定位置的协议号。它不是完整UDP合法性验证器，因此一个IPv4 IHL畸形的输入仍可能通过捕获过滤。裸udp不自动覆盖VLAN里的内层UDP；对IPv6扩展链的处理也不同于应用解析器。

核查后将捕获UDP预期集合修正为[1,5,9,10,11,12,16]；显示UDP集合为[1,5,8,12,15]。二者不同正是阶段语义不同的证据。原失败运行与v1输入/预期保留，v2只修订expected，PCAP字节未变。详细推导见工程tests/BPF-oracle-audit.md和bpf-udp-instructions.txt。

课堂可用这一例回答：“测试失败是否一定是实现错？”答案是否定的。先审查输入、预期来源与所测概念，再定位实现。修改断言必须有独立依据，不能以程序实际输出为唯一理由。
